# פריסה ועדכונים

## יעד האירוח

הגרסה הזו נבנתה ל־Sites, עם שרת Cloudflare Workers, מסד D1 וקבצים ב־R2. ההתחברות האישית מתבצעת בשער ההזדהות של Sites. GitHub הוא מאגר המקור והיסטוריית העדכונים; הוא אינו מסד הנתונים ואינו שירות האירוח.

לא לפרוס את הקוד ישירות ל־GitHub Pages: המערכת דורשת שרת, מסד נתונים ואחסון קבצים. גם פריסה של ה־Worker לבדו ללא שער ההזדהות של Sites אינה שקולה לפריסה נתמכת. מעבר לאירוח עצמאי מחייב התאמה של מנגנון ההתחברות ואימות זהות בשרת.

## התקנה על מחשב חדש

1. לשכפל את המאגר הפרטי ולהיכנס לתיקייה.
2. להתקין Node.js 24 עם npm ולהריץ `npm ci`.
3. להריץ `npm run typecheck` ו־`npm test`.
4. להריץ `npm run build`.
5. במסד מקומי חדש בלבד, להריץ `npm run db:migrate:local`.
6. להריץ `npm run dev`, לפתוח את הכתובת שמוצגת ולהתחבר באמצעות כפתור ההתחברות המקומי. זו זהות בדיקה, לא זהות ייצור.

הסביבה המקומית המקורית נוצרה לפני הוספת פקודת המיגרציות, באמצעות הפעלת SQL ידנית. אין להפעיל בה שוב את המיגרציה הראשונה. הפקודה החדשה מיועדת למסד חדש עם מעקב מיגרציות, ובהמשך תריץ רק מיגרציות שלא הופעלו.

## תהליך עדכון שוטף

1. יוצרים ענף עבודה, לדוגמה `git switch -c update/policy-form`.
2. משנים את הקוד או מבקשים מ־Codex לבצע שינוי במאגר הזה.
3. מריצים `npm run typecheck`, `npm test` ו־`npm run build`.
4. שומרים את השינוי עם commit ודוחפים לענף: `git push -u origin update/policy-form`.
5. פותחים Pull Request אל `main`, ממתינים לבדיקת **Check and package**, וממזגים לאחר בדיקה.
6. מפרסמים את ה־commit הממוזג ל־Sites לפי ההוראות בהמשך.

לעדכון קטן ניתן גם לערוך קובץ בממשק GitHub ולשמור לענף חדש. כל השינויים נשמרים בהיסטוריה; אין צורך ליצור מחדש אתר או מאגר.

## מה GitHub Actions עושה

כל Pull Request וכל עדכון ב־`main` מפעילים התקנה נעולה, בדיקת TypeScript, בדיקות הרשאות, בנייה ויצירת חבילת פריסה. ב־Actions אפשר גם לבחור **Run workflow**.

התוצאה היא artifact ששמו כולל את מזהה ה־commit, ובו:

- `bituach-beklik.tar.gz`: הבנייה, הגדרות Sites והמיגרציות.
- `release.json`: מזהה ה־Site, מזהה ה־commit, חתימת SHA-256 ומועד הבנייה.

החבילה אינה כוללת את נתוני הלקוחות, מסמכים שהועלו, מאגר מקומי או סודות. בדיקה ירוקה אינה מעידה שהאתר פורסם. אין בתהליך הזה אסימון פרסום קבוע ואין פרסום אוטומטי.

## פרסום ל־Sites

זהו מזהה ה־Site הקיים: `appgprj_6ae8214e8c3c8191849ab4aff1c7f4e1`. יש לשמור עליו בעדכונים, יחד עם הקשרים הקיימים ל־DB ול־BUCKET.

אפשר לבקש מ־Codex, עם חיבור GitHub ו־Sites פעיל:

> משוך את הגרסה האחרונה מענף main במאגר ביטוח בקליק שלי ופרוס אותה ל־Site הקיים שמוגדר ב־.openai/hosting.json. שמור על הגישה הפרטית, על מסד הנתונים ועל המסמכים. אמת את הצלחת הפריסה והחזר את הכתובת.

תהליך הפרסום חייב לסנכרן את אותו מקור למאגר המקור של Sites, לבנות ולארוז מאותו commit, לשמור גרסת Site ולפרוס אותה. מזהה ה־commit במאגר המקור של Sites עשוי להיות שונה מזה של GitHub; אין להעביר מזהה GitHub כתחליף לאימות המקור של Sites. יש לאמת את התוצאה בכלי הפרסום.

המאגר והתהליך מוכנים לכך, אך פרסום ייצור תלוי בחיבור פעיל ובהרשאות פרסום ל־Sites. סנכרון/פרסום Sites לא הושלמו במפגש ההקמה המקורי; אין כתובת חדשה מאומתת של המערכת המורחבת עד שפרסום כזה מסתיים בהצלחה.

## מסד נתונים וקבצים

מיגרציות חדשות מתווספות דרך `npm run db:generate`. אין לשנות SQL של מיגרציה שכבר הופעלה. יש לבדוק מיגרציות על עותק בדיקה; פרסום קוד אינו סיבה למחוק או ליצור מחדש מסד או דלי קבצים.

נתוני הבדיקה המקומיים אינם מועברים אוטומטית לייצור. גיבוי הממשק נועד לשחזור באותה סוכנות. העברה מסביבה מקומית לסוכנות ייצור חדשה דורשת תהליך מעבר מפורש עם התאמת שיוך המשתמשים והסוכנות; אין להעלות לשם כך מסד או גיבוי ל־GitHub.

## שחזור גרסה

אם עדכון נכשל, אפשר לפרוס מחדש גרסת Sites קודמת או לבצע `git revert` ל־commit, למזג ולפרוס שוב. שחזור קוד אינו מבטל מיגרציות ואינו משחזר נתונים שנמחקו. לפני שינוי נתונים משמעותי יש לשמור גיבוי. מיגרציית תיקון מתווספת כמיגרציה חדשה.
